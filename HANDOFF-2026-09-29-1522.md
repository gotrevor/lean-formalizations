## 🧠 Context to carry forward

The mental model that makes this whole family of files go: **the strength of the Hermite–Lindemann
form you reach for is determined by whose coefficients the witness polynomial has.** `Bedrock.lean`
discovered this for `sin`/`cos` (witness `X² − 2(cos a)X + 1` has *algebraic*, not rational,
coefficients, so you need `transcendental_algClosure_cexp`, transcendence over `ℚ̄`). This lap
found the dual: **`tan` does not need the strong form at all**, because it is not a quadratic in
`e^{ia}` — the relation `z²(t+i) = i−t` is *linear in `z²`*, so `e^{2ia} = (i−t)/(t+i)` is algebraic
over `ℚ` outright and the weak `transcendental_cexp_of_algebraic` at `2ai` suffices. Reach for the
weak form first and only escalate when the coefficients force you to.

Second model: **Baker applications should never touch `LinearIndependent` directly.** I built
`baker_relation`, which repackages `BakerHomogeneous` via `Fintype.linearIndependent_iff` +
`Algebra.smul_def` into "any `ℚ̄`-relation `c₀·1 + Σ cᵢλᵢ = 0` among `1` and `ℚ`-independent logs of
algebraics is trivial". Both Baker statements then reduce to: exhibit coefficients in
`integralClosure ℚ ℂ`, exhibit the sum, read off which coefficient is visibly nonzero. Future Baker
work should go through this leaf.

Design decision worth knowing on `2^√2·3^√3`: the file header suggested "take a `ℚ`-basis of
`log 2, log 3, log γ`". I did **not** do that — building a basis in Lean is painful. Instead the
third logarithm is `μ = √2 log2 + √3 log3` *itself* (its exponential is exactly the number assumed
algebraic), and I case-split on whether `![log2, log3, μ]` is `ℚ`-independent. Independent → Baker
at `n=3` with coefficient `−1` on `μ`. Dependent → the dependency must have `g₂ ≠ 0` (else it
contradicts independence of `log2, log3`), so `(g₀+g₂√2)log2 + (g₁+g₂√3)log3 = 0`, and Baker at
`n=2` forces `√3 ∈ ℚ`. Two Baker calls, no basis machinery. Recommend this shape whenever a
"choose a basis" step appears in a route sketch.

## ⚠️ Gotchas

- **Plain `simp` rewrites `((Real.log 2 : ℝ) : ℂ)` into `Complex.log 2`.** After that
  `Complex.ofReal_im` no longer fires and every imaginary-part argument stalls with an unsolvable
  `(Complex.log 2).im + 2π = 0` goal. Two defenses, both used here: write `2πi` as
  `((2 * Real.pi : ℝ) : ℂ) * Complex.I`, and use `simp only` with
  `Complex.mul_I_im` / `Complex.mul_I_re` instead of plain `simp`. (`-Complex.ofReal_log` does
  *not* help — that lemma isn't the one firing.)
- `Subalgebra.ofNat_mem` does not exist. For `(2 : ℂ) ∈ integralClosure ℚ ℂ` use
  `by exact_mod_cast Subalgebra.natCast_mem (integralClosure ℚ ℂ) 2`.
- `Fin.sum_univ_three` does **not** fire on a sum over `Fin (n+1)` with `n := 2`. Use
  `Fin.sum_univ_succ` + `Fin.sum_univ_zero` + `Fin.cons_zero`/`Fin.cons_succ` instead, then a
  `show` (defeq) to name the fully-associated goal, then `push_cast; ring`.
- After `fin_cases i` the index appears as `(fun i => i) ⟨0, ⋯⟩`, so `rw [show ![a,b] 0 = a from rfl]`
  fails. Use `show <goal with the value substituted>` — defeq handles it.
- Repo-wide `lake build` shows `sorry` warnings in `DubickasNoSubspace`, `CorvajaZannier*`,
  and vendored `PrimeNumberTheoremAnd/Wiener.lean`. These are **designated-open** (audit surface /
  other campaigns). Don't touch them.
