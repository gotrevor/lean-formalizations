## 🧠 Context to carry forward
The proof is an ordinal-descent argument, built from scratch on `toOrdinal`/`bump`
(NOT `Ordinal.CNF` — I found building the interpretation directly was cleaner than
fighting mathlib's CNF API). The mental model that made it work:

- **The crux is one combined induction.** `toOrdinal b` (read `n` in hereditary
  base `b`, replace `b` by `ω`) needs BOTH strict monotonicity AND the CNF leading
  bound `toOrdinal b n < ω^(toOrdinal b (log b n)+1)` — and each needs the other on
  smaller arguments. They are mutually recursive, so they MUST be proved together
  in a single `Nat.strong_induction_on` (`toOrdinal_mono_and_bound`). I tried to
  prove monotonicity alone first; it's circular — the leading bound quantifies over
  an *unbounded* exponent `e`, so you can't escape needing monotonicity at `(e',e)`.
  The escape is that inside the induction at `n`, every comparison you need is
  between values all `< n` (the leading exponent `log b n < n`, the remainder
  `< n`), so the IH covers them. This pattern is reusable for any hereditary-base→
  ordinal termination proof.
- `bump_mono_and_bound` is the verbatim ℕ-twin (`ω ↦ b+1`); over ℕ many steps
  simplify (`<` IS `+1 ≤`). It exists only to read off the base-`(b+1)` digit
  structure of `bump b n` in the invariance lemma.
- **Invariance** (`toOrdinal_bump : toOrdinal (b+1) (bump b n) = toOrdinal b n`) is
  the structural heart: bumping the base is invisible because both maps read the
  base as `ω`. Proof extracts `log_(b+1)(bump b n) = bump b (log b n)`, the leading
  digit, and the remainder via `Nat.log_eq_of_pow_le_of_lt_pow` + `Nat.mul_add_div`/
  `mul_add_mod`, then recurses.
- Descent: `seqOrd m k := toOrdinal (k+2) (G k)`; `seqOrd_step` (nonzero ⇒ strict
  drop), finished by `Ordinal.lt_wf.has_min` (no infinite descending chain).

Faithfulness was checked empirically BEFORE trusting the def: `#eval` gave
`m=2:[2,2,1,0]`, `m=3:[3,3,3,2,1,0]`, `bump 2 266 = 3^81+81+3` — all hand-verified.
The 14 anchors then nail it via `native_decide` (off the headline axiom path).

## ⚠️ Gotchas
- `Ordinal` is **universe-polymorphic**: a custom `Ordinal`-valued def will spawn
  `u_1` vs `u_2` metavariable mismatches in proofs. Pin the codomain to
  `Ordinal.{0}` (I did this on `toOrdinal`/`seqOrd`) and it all unifies.
- Ordinal addition is only **left**-covariant: `add_lt_add_left` fails to synthesize
  `AddRightStrictMono Ordinal` — use `(add_lt_add_iff_left _).2 h`. Ordinal mult:
  `mul_le_mul_right h a : a*b ≤ a*c` (surprising name — `exact?` it).
- `import Mathlib.SetTheory.Ordinal.Exponential` does NOT bring `ring`/`gcongr` —
  you get "unknown tactic ring". Add `import Mathlib.Tactic.Ring` explicitly.
  `succ_eq_add_one` is `Order.succ_eq_add_one` (from `Mathlib.Algebra.Order.SuccPred`).
- When editing a `.lean` then `#eval`-ing via a scratch file, `lake env lean` uses
  the STALE `.olean` — `lake build` the edited module first or you'll debug a ghost.
